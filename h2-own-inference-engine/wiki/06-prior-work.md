# 6. Prior work

**Core idea:** running language models in a browser has a short but real history. Each project below solved a part
of the problem this engine faces; we borrowed ideas, not code.

| Work | What it is | What we took from it |
|---|---|---|
| [WebLLM](https://arxiv.org/abs/2412.15803) (Ruan, Chen et al., 2024) | LLMs in the browser; WebGPU kernels generated by the MLC-LLM / Apache TVM compilers, WebAssembly for the rest | The bar: up to ~80% of native speed on the same device. Their kernels are compiler-generated; ours are written by hand. |
| [Llamas on the Web / LlamaWeb](https://arxiv.org/abs/2605.20706) (Levine, Sorensen et al., 2026) | A WebGPU backend for llama.cpp, evaluated on 16 GPUs from 8 vendors | Static memory planning (29–33% less memory) and kernels tuned per device; reading GGUF directly, as we do. |
| [llama.cpp](https://github.com/ggml-org/llama.cpp) | The reference C/C++ engine for GGUF models | The Q4_0 / Q8_0 block formats; quantizing the *activations* to 8-bit so the inner loop is an integer dot product; a thread pool where every op splits rows and a barrier separates ops. |
| [wllama](https://github.com/ngxson/wllama) | llama.cpp compiled to WebAssembly (SIMD, threads) | Confirmation that the COOP/COEP headers and a worker-based thread pool are the way to multithread in a browser. |
| [nnJIT](https://arxiv.org/abs/2309.08978) (Jia et al., MobiSys 2024) | Generates and tunes WebGPU / WebAssembly kernels on the user's device | Kernel shape must fit the device; browsers compile shaders with weak optimization, so unrolling and tiling must be explicit. |
| [Anatomizing DL inference in web browsers](https://arxiv.org/abs/2402.05981) (Wang et al., TOSEM 2024) | Measurement study on 50 PCs and 20 phones | In-browser CPU inference was ~17× slower than native on PCs, largely from unused SIMD and runtime overhead: the gap this engine attacks. |
| [Bitnet.cpp](https://arxiv.org/abs/2502.11880) and T-MAC (Microsoft) | CPU kernels for ternary (−1/0/+1) and low-bit weights, with lookup tables | Ideas for the Parakeet encoder's ternary weights (milestone M2). |
| [Chrome: WebAssembly and WebGPU for Web AI](https://developer.chrome.com/blog/io24-webassembly-webgpu-1) | Relaxed SIMD, subgroups, fp16 in WebGPU | The relaxed int8 dot product used by the CPU engine and the subgroups used by the GPU engine. |

## How this engine differs

- **Hand-written, small, readable.** About 1,700 lines in total: the WebGPU kernels and their host code
  ([webgpu.js](../engine/webgpu.js), 630 lines), the C kernels ([kernels.c](../engine/kernels.c), 500 lines) and
  the JavaScript around them. No compiler stack; the CPU build is one ~60 KB WebAssembly file.
- **Shaped for one job.** A voice agent needs short prompts and fast replies on modest machines; the engine keeps
  the conversation's cache and splits threads between prompts and writing.
- **Measured against the libraries it replaces**, on the same model, the same laptop and the same day.

**Bottom line:** the techniques are known (llama.cpp's quantized dot products, WebLLM's and LlamaWeb's WebGPU
work); what this hypothesis adds is a small engine written by hand to learn them, measured step by step on a
modest 2019 laptop.
